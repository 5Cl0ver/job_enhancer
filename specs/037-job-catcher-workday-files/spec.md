# Feature Specification: Job Catcher on Workday (files, Skills, long fills, photos, Submit)

**Feature Branch**: `037-job-catcher-workday-files`

**Created**: 2026-11-27

**Status**: Built

**Input**: The owner's Bugs & ideas reports from two real Apply with Claude runs on Workday. (Examples below use invented companies and people.)

## The six problems, in plain words

- **A. The résumé went in again and again, and was reported "failed".** Workday takes the file from its upload box, empties the box and lists the file in its card a few seconds later. Job Catcher checked the box right after putting the file in, found it empty, and said "failed". It then tried again in the same press, again on each step filled by itself, and dropped it on the zone too: four copies after two presses, each reported as failed.
- **B. A "Resume/Cover Letter" box never got the cover letter.** A box that names both was taken for the résumé's only, so the letter made for the job was never attached.
- **C. "Still filling", then failed.** A long Workday step took more than 90 s to fill. Job Catcher's background stopped waiting at 90 s and reported it as slow (a failure), while the page went on filling; Claude's next fill_page waited only 20 s and got "no report".
- **D. Skills were slow, wrong and missing.** Up to 30 skills, each waiting up to 3.5 s. "Microsoft 365" became "Microsoft 365 Copilot for Sales" (the shortest entry starting with the same words, or the lone result Workday picked by itself). Slow searches were missed (1.5 s wait), "M365" or "Windows 10/11" never matched, skills past 30 were dropped, and nothing said which ones didn't go in.
- **E. "Busy" instead of photos on every page.** The application's tab wasn't showing while the owner used the computer, and Job Catcher never switches tabs while you're active, so every page came back "busy" with no photo and no clear way out.
- **F. A Submit Workday turned down was counted as sent.** Workday disables its Submit while sending, then brings it back with an error. Job Catcher counted a disabled button as "pressed"; the app then locked Submit, so Claude couldn't press it again after fixing the error, and the application was likely never sent.

## What changes

- **A.** A file counts as attached when the page shows it took it: a plain box holds it, or the upload card lists one more file or its name within about 8 s. An emptied box is never a failure; when nothing says either way it's "unverified" (new), never "failed". Each file box is tried once per step of this run (a press or a step filled by itself): never again while its list shows the file Job Catcher put there (a second press, a fresh Job Catcher after a reload), and not for 3 minutes after an unverified try. Once Job Catcher's file is gone from the list (removed, a Page Error and a sign-in), the next press puts it in again. A file of the same name Job Catcher never put there (a returning applicant's old résumé, the same "<Name> - Cover letter.pdf" from another job) never stops ours. For Job Catcher's own file, its name anywhere in the list ("Uploaded: …") or shortened ("Sam_Rivera_Nor….pdf") also counts. Otherwise a list entry counts only for the whole file name (case, spaces, its size and "Successfully Uploaded!" aside), never part of one ("CV.pdf" is not "Old CV.pdf"). What was tried is kept for the tab and the run (the full address, query too), so a reloaded Job Catcher doesn't try again either; another run starts afresh. At most one drop on Workday's zone, after the longer wait, and only when the box still holds the file. A listed file's name is never read as the box's question.
- **B.** A box whose label, the words just before it, or the part of the page holding it alone names the résumé and the cover letter is a box for both: the résumé goes in, then the job's letter, each once. A heading over two separate boxes is never "both". A plain box that takes one file keeps the résumé. The fill now says what happened to the cover letter (`cover_letter`: attached / unverified / no_box / no_file / failed) next to the résumé, and Claude is told what to do about each.
- **C.** After the press's 90 s, or when a fill is already going on the page, Job Catcher waits for that page's own report (every frame's, never a report from a panel action such as Fix or Undo) until 170 s after Claude asked for the fill (by the request's age as the app counts it, never mixing clocks; at least 30 s), so never past the app's own wait, and hands it back as done. Only a page that never reports is "slow". Photos and other requests never wait behind it, and a tab is never shown or photographed while a fill is going on it: Job Catcher waits up to ~30 s, else the photo is missed as "still filling" (the answers kept) and Claude calls page_done again.
- **D.** Skills take only the site's own entry: the same words (case, spaces and punctuation aside) or a known other name (M365 = Microsoft 365, O365 = Office 365, AD = Active Directory); "Windows 10/11" is tried as "Windows 10" and "Windows 11". Workday's qualified entries count: "Python (Programming Language)" for Python, "Amazon Web Services (AWS)" for AWS or Amazon Web Services. Letters of any language count; a skill with no letters or digits never matches. A chip Workday adds by itself that isn't the skill comes off again. The wait for results ends as soon as they show without the skill, or say "No Items", and allows up to 2.5 s for a slow search. The whole box takes about 30 s at most; the skills the site doesn't offer, or that didn't fit in the time, are listed for the user and Claude ("Skills not added: …"). Other search boxes (How did you hear about us?, schools) are unchanged.
- **E.** The rule stays: never switch tabs while you're using the computer. Job Catcher now looks again every 2 s for about 30 s and takes the photos as soon as the tab is showing or you step away. If not, the result says: "Your application tab wasn't showing while you used the computer. Ask the user to click the application's tab, then call page_done again to retake the photos."
- **F.** A Submit with no form of its own counts as pressed only when the page moves to a new address, a confirmation shows, or every copy of the button is gone for 5 s with no error showing. Disabled doesn't count. Job Catcher says it didn't go through only when, 20 s or more after the press, Submit is showing, enabled, AND a new error is on the page (sent with the error: short, no email addresses or long numbers); still sending, just gone or no error says nothing. It keeps watching for about 2 minutes, after a turn-down too, so a late success is still reported. While a press's outcome is pending (about 25 s, until it's known), Job Catcher stops another Submit press itself, and the app tells Claude that the first press is still going through (never "the user hasn't decided yet"; a press stopped after Submit was pressed says it was already pressed). The app logs "Submit didn't go through: …", clears the press so ONE more press is allowed (the lock comes back with it), and tells Claude to read the error, fix it and press Submit once (only "the page shows an error" when one was caught). The page's error goes beside that as data (`submit_error_on_page`), never inside the instruction. At most two such unlocks: the third turn-down keeps Submit locked and Claude is told not to press again and to ask the user to check the page. A confirmation within 10 minutes of a turn-down still ends the run as sent. When the user submits it themselves, a turn-down is theirs: ignored.
- Live boxes Job Catcher sends carry `required: true` for a box the form marks required.
- The playbook says what `cover_letter` and `unverified` mean, and that a "Resume / Cover Letter" box gets both (2026.12.05).
- Job Catcher 0.49.0. The app's page photos say "Résumé put in: check it shows" for an unverified résumé.

## Safety rules that still hold

Passwords are never filled; nothing is submitted by Job Catcher; Submit stays locked until the user's OK (one retry only after the page showed it didn't go through); tabs are never switched while the user is active; agreements and self-identification are never ticked or filled; page text (a step's name, an error) is data, never inside a `next` instruction; nothing about the file but whether it was tried is kept, and only in the browser session.

## Acceptance tests

- **A**: on a Workday-like page that reads the file, empties its box and lists it: exactly one upload and `resume: attached` after a press, a second press and a step filled by itself; ours listed and a fresh Job Catcher → nothing attached, attached; a same-name file that was never ours → ours goes in; ours gone from the list → in again; an unverified try locked 3 minutes only; another address (query) or run → tried afresh; "CV.pdf" never matches "Old CV.pdf"; a list that shows the file 6 s later → one upload, no drop; never listed → `unverified`, no drop, never tried again, a fresh Job Catcher neither; a React zone that ignores the box → one drop. (`test/workday-files-037.spec.js`, `test/job-catcher-fixes.spec.js`, `e2e/workday-files-037.spec.js`, lab `apply-workday-steps.html?change&clear[&late=6000]`)
- **B**: "Resume/Cover Letter", "Résumé and cover letter", "Upload your CV or cover letter" are both; a heading over two boxes isn't; résumé + letter → exactly two files, filled again → still two, `cover_letter: attached`; no letter → the résumé only; a plain multi-file box holds both, a one-file box the résumé (`no_box`); a letter box with no letter → `no_file`; the server keeps and explains `cover_letter`. (`test/workday-files-037.spec.js`, `e2e/workday-files-037.spec.js` with `&shared`, backend `tests/test_apply_job_catcher_037.py`)
- **C**: a press that comes back slow, then the page's report 30 s later → that report as done; never a report → still slow; a busy press whose fill reports after 40 s → that report. (`test/apply-mode.spec.js`)
- **D**: "Microsoft 365" with only "Microsoft 365 Copilot for Sales" offered (and Workday picking it by itself) → no chip; O365, AD, "Windows 10/11", "powershell" → Office 365, Active Directory, Windows 10, Windows 11, PowerShell; a 1.9 s search is waited for; "No Items" ends the wait at once; the box keeps to its budget and lists the rest; "Skills not added: Cobol, Fortran" in what needs you. In the browser lab with slow results and auto-picking: the right five chips and "Skills not added: Microsoft 365, Cobol". (`test/workday-files-037.spec.js`, `e2e/workday-files-037.spec.js`, lab `workday-sections.html?slowSkills=1800&autopick`; spec 020's and 036's tests unchanged)
- **E**: busy, then away after two looks → the photos are taken and the user's tab put back; the user clicks the application's tab meanwhile → photos, nothing switched; busy the whole time → no switch, `busy` after ~30 s of looking, the answers kept; the server's busy text says to ask the user to click the tab and call page_done again, and page_done again takes the photos. (`test/apply-mode.spec.js`, backend `tests/test_apply_job_catcher_037.py`)
- **F**: Workday's Submit disabled, then drawn again with an error → never "pressed", one "didn't go through" with the error (emails and phone numbers taken out); still disabled after 30 s, or back with no error → nothing said, and a success 40 s on is still reported; a second press while the first is pending is stopped, and allowed after the turn-down; a late confirmation after a turn-down is reported; gone 5 s with no error, or a confirmation → pressed. On the server, `submit_failed` clears the press (Submit unlocked), logs the scrubbed error, `wait_for_you` says to read the error, fix it and press once (the error beside it as data; plain words when none was caught), and the next press locks it again; the third turn-down stays locked and says stop and ask the user; a confirmation after a turn-down ends the run as sent; with "I'll submit it myself" it's ignored; each request says when it was made. Live boxes carry `required`. (`test/apply-mode.spec.js`, backend `tests/test_apply_job_catcher_037.py`)
